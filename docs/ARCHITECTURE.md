# AgentOS — архитектура

Провайдер-независимая система автономных агентов: человек ставит
абстрактную задачу в чате, дальше всё делает агент — подключает субагентов,
навыки и доступы, следит за бюджетом токенов, переживает обрывы сессий и
исчерпание лимитов, проверяет собственный результат и учится на прогонах.

## 1. Что здесь необычного

Три решения определяют всю остальную конструкцию.

**Состояние живёт на диске, а не в контексте чата.** Всё — миссии, DAG
задач, критерии приёмки, расход токенов, факты и уроки — лежит в SQLite и
чекпоинтах. Поэтому «продолжить работу» не требует ни человека, ни
транскрипта: следующая сессия читает `var/resume.json` и идёт дальше.

**Субагент получает бриф, а не транскрипт, и возвращает отчёт, а не
транскрипт.** Контекст главного агента растёт как «число задач × размер
отчёта», а не как сумма всех диалогов. Это единственный способ дать
абстрактную задачу и не упереться в контекст на середине.

**Провайдер — деталь реализации.** Anthropic, OpenAI, Google и mock
приведены к одному контракту, включая нормализацию ошибок. Из этого
бесплатно получается то, что иначе стоило бы дорого: критик проверяет
работу на модели **другого** провайдера, а исчерпание лимитов у одного не
останавливает работу.

## 2. Слои

```
┌ Точка входа: AGENTS.md / CLAUDE.md / GEMINI.md ── читает любой агент-хост
├ CLI agentctl ──────────────────── единственный интерфейс к системе
├ Оркестрация: intake → planner → scheduler → dispatch → critic → improve
├ Роли: config/agents/*.yaml — приоритеты, тиры, триггеры, инструменты
├ Возможности: инструменты · MCP-клиент · навыки · доступы
├ Память: рабочая · эпизодическая · семантическая · процедурная · артефакты
├ Провайдеры: anthropic · openai · google · mock + роутер по тирам
└ Состояние: SQLite + JSONL-журнал, чекпоинты, леджер, квоты
```

## 3. Два режима исполнения

Один и тот же бриф, два способа его выполнить:

| Режим | Кто запускает субагентов | Когда используется |
|---|---|---|
| `native` | агент-хост: Claude Code, Codex CLI, Gemini CLI | по умолчанию, когда API-ключей нет: их и не требуется |
| `direct` | сам AgentOS через адаптер провайдера | когда есть ключи; нужен для неприсмотренных прогонов |

В `native` система готовит задание, кладёт его в
`var/runs/<миссия>/briefs/<задача>.md` и ждёт `agentctl task report`.
В `direct` она сама крутит цикл tool-use. Планирование, память, бюджеты,
чекпоинты и проверка результата в обоих режимах одни и те же.

## 4. Память

| Слой | Где | Зачем |
|---|---|---|
| Рабочая | собирается в рантайме | бриф под конкретный шаг; ужимается под бюджет |
| Эпизодическая | `events` + `var/events/*.jsonl` | ход работы; сжимается в дайджест для новой сессии |
| Семантическая | `facts` + FTS5 + векторы | факты, уроки, решения; гибридный поиск |
| Процедурная | `skills/*/SKILL.md` | навыки; в контекст идут только заголовки |
| Артефакты | `var/artifacts/` | файловые результаты, адресуются по хешу |

**Поиск гибридный:** BM25 по FTS5 плюс косинус по векторам, слияние через
Reciprocal Rank Fusion. Ключевые слова находят имена файлов и точные
формулировки, векторы — перефразировки; ни один способ по отдельности не
покрывает оба случая. RRF выбран потому, что не требует калибровать
несопоставимые шкалы BM25 и косинуса.

**Векторы — полный перебор** в двух исполнениях с одним интерфейсом: numpy,
если он установлен, иначе чистый python (`memory.vector.backend`; `off`
оставляет только BM25). ANN-индекса намеренно нет — см. ADR 0002.
Эмбеддинги берутся у провайдера, а без ключей считаются локально
детерминированным хешированием: тесты и работа офлайн идут по тому же коду,
что и боевой режим.

**Навыки раскрываются постепенно.** В контекст попадает строка «имя:
описание», тело подтягивается инструментом `skill_load` по необходимости.
Десяток навыков иначе съел бы контекст раньше самой задачи.

## 5. Экономия токенов

1. **Бриф вместо транскрипта, отчёт вместо транскрипта.** Потолок отчёта —
   `budget.subagent_report_tokens`, по умолчанию 1200 токенов.
2. **Тир по сложности.** Чтение и разметка — `nano`/`small`, код и анализ —
   `large`, планирование и критика — `reasoning`. Роутер выбирает
   конкретную модель тира по доступности и цене.
3. **Кеш стабильного префикса.** Системный промпт роли помечается
   `cache_control`: при веерном запуске субагентов с общим префиксом это
   прямая экономия.
4. **Бюджет делится по DAG.** Каждая задача получает долю пропорционально
   оценке, часть бюджета всегда остаётся в резерве под критика и
   доработки — иначе проверка упирается в пустой кошелёк.
5. **Ужатие брифа в заданном порядке.** Первыми режутся навыки (их можно
   подтянуть позже), затем память (её можно перезапросить), затем входные
   данные. Цель, критерии и инструкции не режутся никогда: без них задача
   выполняется неверно, а не хуже.

## 6. Устойчивость

Состояния задачи: `PENDING → READY → RUNNING → DONE | FAILED |
BLOCKED_QUOTA | BLOCKED_APPROVAL | BLOCKED_CAPABILITY | CANCELLED`.
Недопустимые переходы — исключение, а не молчаливая порча состояния.

- **Чекпоинт после каждого перехода**, атомарной записью (temp + rename):
  недописанный чекпоинт невозможен.
- **Идемпотентность задач** по `idempotency_key`: повторное планирование
  после краша не плодит дубликаты выполненного.
- **Леджер с `dedupe_key`**: повторно записанный после краша вызов не
  удваивает счётчик токенов.
- **Зависшие `RUNNING` возвращаются в очередь**: оборванная сессия не
  оставляет вечно «выполняющихся» задач.
- **Исчерпание лимита — пауза с известным концом.** Задача уходит в
  `BLOCKED_QUOTA` с `resume_after`, провайдер помечается в таблице `quota`,
  роутер переключается на другого провайдера того же тира, **остальные
  ветки DAG продолжают идти**.

Три триггера продолжения, все не требуют человека: SessionStart-хук
агент-хоста, `scripts/headless.sh` для неприсмотренных прогонов и
`make resume` вручную.

## 7. Самопроверка

Порядок принципиальный:

1. **Программные гейты** (`make test`, `make lint` — задаются в
   `config/agentos.yaml`) выполняются первыми. Красный гейт = отказ,
   независимо от мнения модели.
2. **Критик** проверяет семантические критерии, по возможности на модели
   другого провайдера, чем автор результата.
3. **Отказ не эскалируется человеку сразу**: система заводит задачи на
   исправление и пробует довести работу сама, до `MAX_FIX_ROUNDS` раундов.

Источник правды о готовности — таблица `dod`, а не отсутствие оставшихся
задач. Миссия становится `DONE`, только когда каждый критерий имеет статус
`pass` (или `skipped` — так помечается гейт, который не запускался, чтобы
пропуск не выдавался за проверку). В native-режиме вердикт по смысловым
критериям выносит агент-хост через `agentctl verify --verdict`: своей модели
у системы там нет. Красный программный гейт отменяет любой вердикт, чей бы
он ни был.

Критерии приёмки фиксируются **до** начала работы. Иначе «готово»
определяется постфактум тем же агентом, который делал работу, — и проверка
превращается в самоподтверждение. Нераспознанный ответ критика трактуется
как `needs_human`, а не как согласие: молчание не согласие.

## 8. Самоулучшение

После успешной миссии эпизоды сжимаются в факты и уроки, а повторяющиеся
удачные процедуры оформляются в черновики навыков в `skills/_proposed/`.
Черновик **не активируется автоматически**, пока это не разрешено в
конфиге: самопишущийся навык, попавший в контекст всех будущих задач, —
самый дорогой способ закрепить ошибку. От регрессий защищают эталонные
миссии в `evals/`.

## 9. Безопасность

- **Allowlist вместо блеклиста**: пути записи, бинари команд, хосты сети.
  Оболочек (`sh`, `bash`) в списке нет — они обошли бы весь allowlist.
- **Гейты подтверждения** вместо запретов: необратимое действие (push,
  запись вне allowlist, установка пакетов) переводит задачу в
  `BLOCKED_APPROVAL`, а остальные ветки продолжают идти. Запрос ложится в
  очередь `approvals` и живёт там между сессиями: `agentctl approve list`,
  затем `grant` возвращает задачу в очередь исполнения.
- **Секреты только через окружение.** Они не попадают ни в БД, ни в журнал,
  ни в отчёты: редактор вырезает их по маскам и по значениям «секретных»
  переменных окружения. Агент не добывает доступы сам — он формулирует один
  точный запрос человеку.
- **Mock не подменяет провайдера.** Он включается только явным
  `AGENTOS_ALLOW_MOCK=1`; иначе выдуманный ответ выглядел бы как результат
  работы.
