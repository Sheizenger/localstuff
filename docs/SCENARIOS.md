# Сценарии взаимодействия

Восемь ситуаций, ради которых система построена. Везде исходная позиция
одна: человек говорит, что хочет, и не следит за процессом.

## 1. Абстрактная задача

```
Человек: сделай так, чтобы в проекте появилась нормальная документация
```

Агент выполняет `agentctl goal "..."`. Система:

1. фиксирует критерии приёмки **до** работы (`agentctl mission dod <id>`);
2. строит DAG задач, помечая независимые как параллельные;
3. подбирает роли по триггерам (`researcher`, `coder`, `reviewer`, …);
4. выдаёт задания и делит бюджет токенов между ними.

Человек видит одну карточку: цель, критерии, сколько задач сделано, расход.
Уточняющий вопрос задаётся, только если без ответа работа пойдёт заведомо
не туда, и не больше двух за миссию.

## 2. Кончились токены посреди работы

Провайдер вернул ошибку лимита. Система:

- переводит задачу в `BLOCKED_QUOTA` с точным `resume_after`;
- помечает провайдера в таблице `quota`, роутер переключается на другого
  провайдера того же тира, если он настроен;
- **остальные ветки DAG продолжают идти**;
- пишет чекпоинт и обновляет `var/resume.json`.

Человек не делает ничего. Следующая сессия начинается с
`agentctl resume --announce` и печатает одну строку:

```
AgentOS подхватил: навести порядок в документации [3/7, продолжит через 42м]
```

## 3. Сессия оборвалась или процесс убит

`resume` читает последний чекпоинт. Выполненные задачи не переигрываются
(идемпотентность по ключу), израсходованные токены не пересчитываются
(`dedupe_key` в леджере), зависшие `RUNNING` возвращаются в очередь.

## 4. Человек хочет иначе

```
Человек: пусть отчёт будет не в markdown, а в html
```

Правится DoD, а не код:

```bash
agentctl mission dod <id> --add "отчёт в HTML, открывается в браузере"
agentctl resume
```

Перепланируется только затронутая часть: задачи идемпотентны по ключам,
уже сделанное не переделывается.

## 5. Не хватает доступа

Субагенту нужен MCP-сервер или ключ. Он вызывает `capability_request`,
резолвер проверяет каталог и политику:

- разрешено и есть всё нужное → подключает сам, работа идёт дальше;
- нужен секрет → задача уходит в `BLOCKED_CAPABILITY`, **остальные ветки
  продолжают идти**, а в `agentctl status` появляется ровно один понятный
  пункт: какую переменную окружения задать.

Агент не добывает доступы в обход политики и не встаёт целиком.

## 6. Результат не прошёл проверку

Гейты красные или критик отклонил. Система не идёт к человеку — она заводит
задачи на исправление и пробует довести работу сама (до двух раундов).
Только после этого — эскалация с конкретным списком, что именно не сошлось.

Красный программный гейт — отказ, который нельзя переспорить вердиктом
модели.

## 7. Система учится на прогоне

После успешной миссии:

- факты и уроки уходят в семантическую память
  (`agentctl memory search "как запускаются тесты"`);
- повторяющиеся удачные процедуры оформляются в черновики навыков в
  `skills/_proposed/`;
- черновик активируется только явно: `agentctl skill promote <имя>`
  (или автоматически, если в конфиге разрешён `auto_promote_skills`);
- от регрессий защищают эталонные миссии: `agentctl eval run`.

## 8. Провайдер сменился

Ключ отозвали, лимит выбран, модель недоступна — роутер берёт другую модель
того же тира у другого провайдера. Если и там пусто, тир понижается
(`reasoning → large → small → nano`). Состояние миссии при этом не
теряется: провайдер записан в задаче, но не определяет её.

## Типовая сессия целиком

```bash
make bootstrap              # один раз
make doctor                 # проверить окружение и ключи

agentctl goal "собери и опубликуй обзор архитектуры"
# ... агент-хост выполняет выданные задания своими субагентами ...
agentctl task report t_ab12 --json '{"summary":"…"}'
agentctl resume             # следующая порция заданий или проверка

agentctl status             # что сделано, что блокирует, когда продолжит
agentctl verify <mission>   # прогнать гейты и критика по требованию
```

Для полностью неприсмотренного прогона (нужны ключи):

```bash
bash scripts/headless.sh    # крутит миссии до конца, уважая лимиты
```
